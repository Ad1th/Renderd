Questions & Answers

Frequently Asked Questions

Everything you need to know about Renderd's design choices, latency targets, security model, and platform requirements.

Questions

Renderd combines four latency-optimized architectural choices:

  1. Zero-copy hardware pipelines: Direct IOSurface GPU frame binding with ScreenCaptureKit and VideoToolbox on macOS, matched with Direct3D12 hardware decoding on Windows.
  2. QUIC Datagrams (RFC 9221): Low-overhead UDP transport with zero head-of-line blocking and zero handshake latency for active sessions.
  3. Vsync Phase Synchronization (RFC-0002 §7): Host frame capture is scheduled dynamically to land 2–5ms before the viewer's display refresh boundary, eliminating the 8.3ms average dual-vsync penalty.
  4. No jitter buffer: Jitter buffers add 16–33ms of static latency. On wired Gigabit LANs (or 5GHz 802.11ax Wi-Fi), jitter is under 1ms, rendering jitter buffers unnecessary.

Existing open-source tools (like Sunshine and Moonlight) are heavily optimized for Windows host PCs streaming to client devices. However, many developers and creators use a macOS workstation (Mac Studio, MacBook Pro) alongside a high-refresh-rate Windows PC setup.

Apple Sidecar only streams to iPadOS devices, and Luna Display requires commercial hardware dongles. Renderd fills this exact gap: an open-source, lightweight daemon optimized specifically for streaming Apple Silicon host displays to Windows 10+ desktop displays.

Zero. Renderd is 100% peer-to-peer over your local network. It does not route traffic through cloud relays, require account registration, send telemetry to third-party servers, or gate features behind subscription paywalls.

Raw UDP requires implementing encryption, congestion control, and ordering mechanisms from scratch. WebRTC brings heavy binary overhead (~150MB), lacks standardized H.265 support, and relies on complex signaling architecture.

QUIC (via the quinn Rust library) provides integrated TLS 1.3 encryption, congestion control (NewReno), ordered reliable streams for control signaling (Stream 0), and unreliable/unordered datagrams (RFC 9221) for video frames — all in a tiny 5MB footprint without intermediary servers.

Pairing is a one-time ceremony using SPAKE2+ (RFC 9382). The host displays a 6-digit PIN. Entering the PIN on the viewer performs mutual authentication without transmitting secret keys.

Both devices derive a PairToken stored securely in system keychains (macOS Keychain Services & Windows Credential Manager) and generate self-signed TLS certificates. All future sessions authenticate automatically via mutual TLS (mTLS).

Software encoding (e.g. x264/x265 on CPU) at 1080p60 introduces 20–50ms of CPU encode latency and heavy core utilization. Renderd explicitly rejects sessions if hardware acceleration is unavailable (ERROR_NO_HW_CODEC) to guarantee display-class responsiveness.

Documentation

Renderd is a peer-to-peer display streaming daemon that mirrors a macOS host display to a Windows 10+ viewer at display-class latency (≤ 30 ms glass-to-glass at 1080p60 on Gigabit LAN) without any cloud relay or intermediary server.

Prerequisites

Before building, ensure you have the following installed:

All Platforms

  • Rust stable 1.80+ — install via rustup.rs
  • The toolchain is automatically selected from rust-toolchain.toml in the repository root

macOS (Host Development)

  • macOS 14.0+ (Sonoma) on Apple Silicon (M1 or later)
  • Xcode Command Line Tools: xcode-select --install

Windows (Viewer Development)

  • Windows 10 or later
  • Visual Studio 2022 with Desktop development with C++ workload
  • Windows 10 SDK (included in VS2022 C++ workload)

Building

Clone the Repository

git clone https://github.com/Ad1th/renderd.git
cd renderd

Check Workspace Compilation

# Check all crates (fast — no code generation)
cargo check --workspace

# Build with full optimization
cargo build --workspace --release

Generate Protobuf Types

The renderd-proto crate requires running proto-gen after any changes to proto/renderd.proto: 

cargo run --manifest-path tools/proto-gen/Cargo.toml
💡
The CI workflow automatically validates that generated proto files are up to date. If you modify renderd.proto and forget to regenerate, the CI check will fail.

Platform-Specific Builds

# macOS host daemon only
cargo build -p renderd-host --release

# Windows viewer only
cargo build -p renderd-viewer --release `
  --target x86_64-pc-windows-msvc

Running Tests & Verification

# Code formatting check
cargo fmt --check

# Strict workspace Clippy lints (must pass in CI)
cargo clippy --workspace --all-targets -- -D warnings

# Execute test suite (cargo-nextest for faster output)
cargo nextest run --workspace

# Standard cargo test (fallback)
cargo test --workspace

# Dependency & license audit
cargo deny check

Host Configuration

Configuration is loaded from multiple sources in order (each overrides the previous): built-in defaults → renderd-host.toml → RENDERD_* env vars → CLI flags. 

# renderd-host.toml (example)

[host]
# Target capture frame rate
fps = 60

# Primary codec: "h265" or "h264"
codec = "h265"

# Display index (0 = primary display)
display_index = 0

[network]
# QUIC listen port
port = 9901

# Max concurrent QUIC datagrams in flight
max_datagrams_in_flight = 64

[abr]
# Adaptive bitrate bounds (kilobits per second)
min_bitrate_kbps = 2000
default_bitrate_kbps = 20000
max_bitrate_kbps = 50000

[crypto]
# macOS Keychain service name for PairToken storage
pair_token_keychain_service = "renderd-pair"

Viewer Configuration

# renderd-viewer.toml (example)

[viewer]
# Preferred display output (0 = primary)
display_index = 0

# Allow DXGI tearing (auto-detected if omitted)
allow_tearing = true

[network]
# Explicit host IP (overrides mDNS discovery)
# host_ip = "192.168.1.100"
host_port = 9901

Control Plane Protocol

All control messages are sent over QUIC Stream 0 using length-prefixed Protobuf encoding: 

[u32 big-endian message length][Protobuf Envelope bytes]

Key message types (defined in proto/renderd.proto):

MessageDirectionPurpose
SessionHelloBoth → BothProtocol version negotiation, capabilities
SessionConfigHost → ViewerCodec, resolution, bitrate parameters
VsyncReportViewer → HostVsync phase for clock synchronization (every ~16.7ms)
ReactiveStatsViewer → HostFragment loss & jitter for ABR (every 100ms)
PeriodicStatsViewer → HostLong-term bitrate feedback (every 500ms)
KeyframeRequestViewer → HostRequest I-frame on excessive fragment loss
SessionEventBoth → BothPairing, reconnect, disconnect events
ErrorBoth → BothProtocol violations, fatal conditions

Data Plane Protocol

Video frame fragments are sent as QUIC datagrams (RFC 9221 — unreliable, unordered). Each datagram starts with a 16-byte fixed binary header:

FieldSizeTypeDescription
frame_id4 bytesu32 BEMonotonically increasing frame identifier
fragment_index1 byteu8Fragment's position within the frame (0-based)
fragment_total1 byteu8Total fragments for this frame
flags1 byteu8Bitfield: KEY_FRAME (0), LAST_FRAGMENT (1), H264 (2)
payload_len2 bytesu16 BELength of the following NAL payload
reserved7 bytes—Reserved for future use (must be zero)

Pairing Flow

Pairing is a one-time ceremony that establishes mutual authentication between a specific host and viewer. It uses SPAKE2+ (RFC 9382) with a 6-digit PIN.

sequenceDiagram participant Host as renderd-host (macOS) participant User as User participant Viewer as renderd-viewer (Windows) Host->>Host: Generate random 6-digit PIN Host->>User: Display PIN in menu bar (60s timeout) User->>Viewer: Select host from discovery list User->>Viewer: Enter PIN Viewer->>Host: QUIC connect (pairing mode) Viewer->>Host: SPAKE2+ shareP (RFC 9382 prover) Host->>Viewer: SPAKE2+ shareV (RFC 9382 verifier) Viewer->>Host: SPAKE2+ confirmP = MAC(K_confirmP, shareV) Host->>Viewer: SPAKE2+ confirmV = MAC(K_confirmV, shareP) Host->>Host: Derive PairToken via HKDF-SHA256 Viewer->>Viewer: Derive PairToken via HKDF-SHA256 Host->>Host: Store PairToken in macOS Keychain Viewer->>Viewer: Store PairToken in Windows Credential Manager Host->>User: UserNotifications: "Paired with [viewer]"

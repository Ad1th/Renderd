System Overview

End-to-End Data Flow

Renderd is a peer-to-peer display receiver. A frame captured on the host must appear on the viewer's physical display in under 30 ms at 1080p60, with a graceful latency gradient at higher resolutions.

§5 Transport Layer

QUIC Dual-Channel Design

A single QUIC connection (RFC 9000 + RFC 9221) carries two logical channels with different reliability guarantees — exactly what Renderd needs.

📋

QUIC Stream 0 — Control Plane

Reliable, ordered. Used for:

  • Session handshake & pairing
  • Codec negotiation (SessionHello / SessionConfig)
  • Vsync phase reports (VsyncReport)
  • Reactive feedback (ReactiveStats, every 100ms)
  • Periodic stats (PeriodicStats, every 500ms)
  • Keyframe requests (KeyframeRequest)
  • Session events & errors
[u32 length][Protobuf Envelope]
📦

QUIC Datagrams — Data Plane

Unreliable, unordered (RFC 9221). Used for:

  • Video frame fragments (H.265/H.264 NAL units)
  • 16-byte fixed binary fragment header
  • Burst-sent per frame for minimum latency
  • Out-of-order arrival handled by sliding-window reassembly
[16-byte FragmentHeader][NAL Payload]
💡
Why QUIC? Raw UDP performance with production-grade TLS 1.3 security, ordered reliable control, and unordered unreliable datagrams for video — all in a single connection without any broker or relay on a LAN. Binary size is ~5 MB with quinn vs 100–200 MB for WebRTC.

§19 Latency Budget

Glass-to-Glass Breakdown

Phase sync reduces the display scanout component from ~8.3 ms (half a frame period, unsynchronized) to ~2 ms (synchronized lead-in) — this is the mechanism that makes the 30 ms target achievable.

1080p60 — Target: ≤ 30 ms

§12 Data Plane Protocol

16-Byte Fragment Header

Each QUIC datagram payload begins with a fixed 16-byte binary header enabling the receiver to reassemble fragments into frames without any additional framing overhead. 

┌──────────┬──────────┬──────────┬──────────┬──────────┬──────────┬──────────┬──────────┐
│  frame_id (u32, BE)  │frag_idx  │frag_total│ flags(u8)│   payload_len (u16, BE)│ reserved │
│     4 bytes          │  1 byte  │  1 byte  │  1 byte  │       2 bytes          │  1 byte  │
└──────────┴──────────┴──────────┴──────────┴──────────┴──────────┴──────────┴──────────┘
                                                    │
                                            FragmentFlags:
                                            bit 0 = KEY_FRAME
                                            bit 1 = LAST_FRAGMENT
                                            bit 2 = H264 (else H265)

Sliding-Window Reassembly Buffer

  • Window depth: W = 4 frames (keyed by frame_id)
  • Fragment deadline: Dynamic — frame_period − decode_latency − render_latency (default 12 ms)
  • Out-of-order handling: Frames outside the window are discarded; window advances on frame complete or deadline expiry
  • Keyframe requests: Sent immediately on excessive frame loss via QUIC Stream 0

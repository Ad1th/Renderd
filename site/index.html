Why it did not
exist before

Cross-platform display extension has been stuck for a decade. Every existing option trades away latency, image quality, or your independence. Renderd refuses all three.

// FAULT 01

Cloud relays & paywalls

Most commercial cross-platform apps route your desktop through a remote server and gate it behind a subscription. Your screen leaves your network to reach a machine three feet away.

Renderd: the two machines talk directly. Nothing transits a third party.
// FAULT 02

Latency & frame stutter

Protocols built on WebRTC or TCP fight jitter and frame pacing, especially on 120 / 144 Hz panels. The result: usable for a static window, a slideshow for anything that moves.

Renderd: QUIC datagrams, vsync phase alignment, keyframe-on-loss recovery.
// FAULT 03

No Mac-host → PC-viewer path

Sunshine / Moonlight and friends are built for a Windows host streaming out. Nothing is purpose-built for a macOS workstation driving a Windows 10+ panel as extra desktop.

Renderd: that is the whole design target — ScreenCaptureKit → Direct3D 12.

[ 03 ]

The pipeline,
stage by stage

Six hand-offs from Mac desktop to Windows panel. Every one is GPU-resident or lock-free; nothing copies a full frame through the CPU.

  1. STAGE 01 · macOS HOST

    Virtual display + zero-copy capture

    The host adds a CGVirtualDisplay sized to your Windows monitor, so the PC is a genuine extra desktop, then captures it with ScreenCaptureKit straight into a GPU IOSurface.

  2. STAGE 02 · macOS HOST

    VideoToolbox hardware encode

    The surface is fed to a real-time VTCompressionSession — HEVC or H.264, CABAC, zero frame reordering, no encoder buffering. Output NAL units land in a lock-free ring.

  3. STAGE 03 · TRANSPORT

    QUIC datagram burst

    Each frame is fragmented behind a 16-byte header and sent as an unreliable datagram burst over quinn. Path-MTU aware, 16 MiB socket buffers, a wide initial congestion window.

  4. STAGE 04 · TRANSPORT

    Sliding-window reassembly

    The viewer rebuilds frames out of order with a bounded window. A lost fragment slides the window and fires an immediate keyframe request rather than wedging the stream.

  5. STAGE 05 · WINDOWS VIEWER

    Hardware decode

    Media Foundation (H.264 everywhere) or ID3D12VideoDecoder (HEVC) turns the bitstream back into NV12. The decoder output queue stays shallow to hold latency down.

  6. STAGE 06 · WINDOWS VIEWER

    Present on the vsync phase

    The viewer reports its DWM vsync phase back over the control stream; the host paces capture to match. Frames are drawn only when a new one arrives — never on a spin loop.

[ 04 ]

Two planes,
one socket

Control-plane signalling rides QUIC stream 0 with Protobuf framing. Data-plane video rides QUIC datagrams with a fixed 16-byte header. They never block each other.

Control plane — handshake, ABR telemetry, vsync reports, keyframe requests Data plane — fragmented frame datagrams, fire-and-forget

Two commands

Build both binaries from the workspace, run the host on the Mac, point the viewer at it from Windows. mDNS finds the host automatically on a flat LAN; --host covers everything else.

▸ TERMINALmacOS · HOST
# build the workspace
$ cargo build --release

# start the daemon — it prints the address to dial
$ ./target/release/renderd-host
  INFO QUIC server listening on 0.0.0.0:4433
  INFO Connect the viewer with:
        renderd-viewer --host 192.168.1.42:4433
▸ TERMINALWINDOWS · VIEWER
# same repo, built on Windows
> cargo build --release

# auto-discover on a flat LAN…
> .\renderd-viewer.exe

# …or dial the host directly
> .\renderd-viewer.exe --host 192.168.1.42:4433
  INFO Stream 0 handshake complete · presenting

A virtual display appears on the Mac at the viewer's resolution. Drag windows onto it like any second monitor. Close the viewer and the display disappears.
